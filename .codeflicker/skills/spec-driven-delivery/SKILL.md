# Spec-Driven Delivery

需求交付的闭环方法：**先定规则，再写代码，最后用可执行证据证明**。

核心主张：多数返工不是因为代码写错，而是因为规则没定清就开工。因此把「澄清」与「验证」提升为与编码同等的必要环节。

## 适用场景

适用：

- 新增功能、修改既有规则
- 非平凡缺陷修复（涉及状态机、并发、边界条件）
- 涉及多端契约的改动
- 放宽既有限制的需求（风险最高，必须走完整流程）

不适用：改错别字、调颜色数值、纯格式化——这类直接做，不必套流程。

## 输入

开工前必须具备以下四项。缺失则先澄清，不可自行假设：

| 输入 | 说明 | 缺失时的动作 |
|---|---|---|
| 需求描述 | 用户想要什么 | — |
| 规则裁决 | 与既有规则冲突时以哪边为准 | 提问，给选项 |
| 滥用边界 | 新能力是否需要代价约束 | 提问，指出漏洞 |
| 失败行为 | 目标不存在/已失效时如何表现 | 提问或提议缺省 |

## 输出

交付物包含四项，缺一不可：

1. **代码改动**：按契约优先顺序完成
2. **计划文档**：需求定义、影响面、关键约束、验收标准
3. **回归脚本**：可执行，产出 `PASS`/`FAIL` 与汇总结论
4. **验证报告**：新增测试结果 + 既有回归结果 + 类型检查/构建状态

## 操作步骤

### 步骤 1：澄清规则（编码前必做）

不要把模糊需求直接翻译成代码。先识别**规则冲突点**与**滥用向量**。

必须主动追问的四类问题：

1. **规则冲突**：新需求是否与已实现的规则矛盾？
   如「允许退出后回归」与既有「退出即作废凭证」直接冲突，必须先让用户裁决，而非默默改掉一边。

2. **滥用向量**：这个能力会被如何利用？
   凡「放宽限制」类需求都要问一遍。允许中途离开再回来，就要问清是否会被用来规避损失。

3. **边界与时限**：状态保留多久？超时后怎么办？空集合、单元素、并发触发分别如何表现？

4. **失败路径**：目标状态已不存在时如何表现？报错、静默降级，还是回退缺省？

提问方式：**给选项而非开放式问句**，标注推荐项及理由。用户负责决策，你负责列出后果。

若用户的选择会引入滥用漏洞，**明确指出并给补偿方案**，而不是照做。例如允许中途退出后回归时，可让退出本身付出等价代价，使收益归零。

### 步骤 2：写计划（改动前落盘）

计划的作用是暴露影响面。至少写清四件事：

1. **需求定义**：用户确认的规则，逐条列出
2. **影响面**：按文件列出改什么，特别标出契约层
3. **关键约束**：容易做错的地方及原因
4. **验收标准**：可判定真假的条目，不写「体验流畅」这类无法验证的描述

若新需求推翻此前决定，**先更新计划原条目再动手**，避免计划与实现漂移。

### 步骤 3：实现（契约优先）

改动顺序：**契约层 → 服务端 → 客户端 → 测试脚本**。

契约先行让类型检查器成为第一道防线。契约一改，所有未跟进的调用点立刻暴露。

四条实践原则：

1. **单一事实源**：共享类型只定义一次，各端重新导出。双份定义各自漂移，编译期无法发现。
2. **兼容缺省值**：新增可选参数要有缺省行为；非法输入回退安全缺省而非抛错。
3. **注释写原因**：解释「为什么」，尤其记录反直觉决定防的是什么问题。
4. **状态语义可区分**：不同来源的相似状态必须可区分。「主动离开」与「意外中断」共用一个标记，后续逻辑必然打架。

### 步骤 4：验证（可执行）

编写脚本化回归，覆盖四类场景：

| 类别 | 说明 |
|---|---|
| 正向 | 需求描述的主路径 |
| 差异 | 同一操作在不同模式/配置下的表现差异 |
| 边界 | 时限到期、集合为空、目标已销毁 |
| 恶意 | 伪造凭证、越权访问、绕过限制 |

优先真实协议交互，需观察内部状态时再直接驱动核心对象。

### 步骤 5：全量回归

跑**全部**既有回归，而非只跑新增的。跨特性破坏常出现在你认为无关的地方。同时确认类型检查、构建、lint 通过。

## 约束

以下为硬性约束：

1. **未经执行验证的功能视为未完成**。「应该没问题」不构成交付。
2. **过时断言必须更新，不可删除**。断言失败若源于本次刻意变更，改写为新行为的断言并在提交信息说明；删除会永久丢失覆盖。
3. **用户选择有漏洞时必须指出**。不可默默照做。
4. **发现既有缺陷先报告再修**。修掉它，但在提交信息单列一段说明。
5. **禁止只跑新增测试**。必须全量回归。
6. **禁止用直觉替代数据**。怀疑某情况不会发生时，跑统计验证。
7. **已知限制必须诚实说明**。给出改进方向，而非掩盖。

## 验证方法

回归脚本必须产出机器可判读的结论：

- 逐项输出 `PASS` / `FAIL` 加**实际观测值**（不只是布尔）
- 汇总行输出 `ALL PASS (N checks)` 或 `FAILED n`
- 全通过退出码 0，否则非 0，便于串入流水线

```
PASS 主动退出即判定淘汰 (已淘汰)
PASS 回归为参战身份 (isSpectator=false)
PASS 回归后输入生效 (936,680 -> 936,747)
PASS 结束后拒绝回归 (code=REJOIN_FAILED)

ALL PASS (11 checks)
```

汇总检查：

```bash
<run-new-test>      | grep -E "ALL PASS|FAILED"
<run-each-existing> | grep -E "ALL PASS|FAILED"
<type-check> && <build> && <lint>
```

骨架与陷阱见 `references/verification-patterns.md`。

## 使用示例

### 示例 1：放宽限制类需求（含冲突澄清）

**用户**：加一个退出后可以主动重连的功能。

**步骤 1 澄清** —— 识别到与既有规则冲突，提问：

```
当前主动退出会作废凭证并判定淘汰，正是为防止「打不过就退出躲伤害再回来」。
若允许原样回归，这个漏洞会打开。

Q1 回归后以什么身份？
   A. 观战身份（推荐：退出即淘汰，回来只能看）
   B. 原席位参战
   C. 按模式区分
Q2 席位保留多久？  A. 至本局结束（推荐）  B. 限时 60 秒
Q3 回归入口在哪？  A. 首页横幅（推荐）    B. 房间列表标记
```

用户选 C / A / A。

**加强约束** —— 指出选项 C 仍有漏洞，提议补偿：主动退出**仍立即判定淘汰**，使「退出」等价于「原地被击杀一次」。死斗模式丢一条命并送对手一个击杀数，经典模式直接失去参战资格。收益归零，不构成免伤利用。

**步骤 2 计划** —— 记录规则调整、影响面（3 个服务端文件 + 4 个客户端文件）、关键约束（需区分「中断待自动恢复」与「已退出待手动回归」两种状态，否则自动重连会绕过手动入口）、验收标准 7 条。

**步骤 3 实现** —— 契约层无需改动（复用既有消息），服务端调整退出分支，客户端加状态标记与回归入口。

**步骤 4 验证** —— 11 项断言覆盖四类场景。首轮暴露一个既有缺陷：

```
FAIL 结束后无法回归 (仍成功)
```

对局结束后仍能回归，玩家会进入无法继续的死局房间。这与本次需求无关，是恢复接口一直缺少终态校验。修复后重跑：

```
PASS 结束后无法回归 (code=REJOIN_FAILED)
ALL PASS (11 checks)
```

**步骤 5 全量回归** —— 一条旧断言失败：

```
FAIL 主动退出后凭证失效 (仍可重连)
```

这正是本次刻意改掉的行为。**改写为新行为的断言**而非删除，并在提交信息中说明。

### 示例 2：多模式类需求

**用户**：分成两个模式，一个无限复活按时间结束，一个一条命最后存活者胜。

**澄清** —— 模式差异必须能穷举成规则列表。追问超时判定：经典模式时间耗尽但多人存活时怎么判？提议「存活优先 → 得分 → 命中数」，即活着的一定赢过死了的。

**验证设计** —— 差异场景是核心，用循环遍历模式跑同一套断言：

```
PASS [deathmatch] 安排了复活 / 4 秒后已复活 / 对局继续
PASS [classic] 不安排复活 / 4 秒后仍淘汰 / 仅剩一人即结束 / 存活者获胜
```

时间推进用临时替换时间函数实现，**用完必须恢复**，否则污染后续用例。

**覆盖率自检** —— 顺手校验配置项是否都被实际使用，发现某主题从不产出 2×2 障碍物，导致对应素材永远不显示。这是既有布局问题，单独报告而非静默忽略。
