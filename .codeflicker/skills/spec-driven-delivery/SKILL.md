# Spec-Driven Delivery

需求交付的闭环方法论：**先定规则，再写代码，最后用可执行证据证明**。

核心主张：多数返工不是因为代码写错，而是因为规则没定清就开工。因此把「澄清」和「验证」提升为与编码同等的必要环节。

## 何时使用

适用：新增功能、修改既有规则、非平凡缺陷修复、涉及多端契约的改动。

不适用：改错别字、调颜色数值、纯格式化——这类直接做，不必套流程。

## 五个阶段

### 阶段 1：澄清规则（编码前必做）

不要把模糊需求直接翻译成代码。先识别**规则冲突点**与**滥用向量**，向用户确认。

必须主动追问的四类问题：

1. **规则冲突**：新需求是否与已实现的规则矛盾？
   如「允许退出后回归」与既有「退出即作废凭证」直接冲突，必须先让用户裁决，而非默默改掉一边。

2. **滥用向量**：这个能力会被如何利用？
   凡是「放宽限制」类需求都要问一遍。允许玩家中途离开再回来，就要问清是否会被用来规避伤害；允许重试，就要问清是否会被用来刷奖励。

3. **边界与时限**：状态保留多久？超时后怎么办？空集合、单元素、并发同时触发分别如何表现？

4. **失败路径**：目标状态已不存在时如何表现？是报错、静默降级，还是回退到某个缺省值？

提问要点：给出选项而非开放式问句，并标注推荐项及其理由。用户只需选择，不必替你设计。

若发现用户的选择会引入滥用漏洞，**明确指出并给出补偿方案**，而不是照做。例如允许中途退出后回归时，可让退出本身付出等价代价，使收益归零。

### 阶段 2：写计划（改动前落盘）

计划不是仪式，作用是暴露影响面。至少写清四件事：

1. **需求定义**：用户确认的规则，逐条列出
2. **影响面**：按文件列出改什么，特别标出契约层（协议/接口/数据结构）
3. **关键约束**：容易做错的地方，以及为什么这样定
4. **验收标准**：可判定真假的条目，不写「体验流畅」这类无法验证的描述

若新需求推翻了此前的决定，**先更新计划中的原条目再动手**，避免计划与实现漂移。

### 阶段 3：实现（契约优先）

改动顺序：**契约层 → 服务端 → 客户端 → 测试脚本**。

契约先行的原因是让类型检查器成为第一道防线。契约一改，所有未跟进的调用点立刻暴露，不必靠人工排查。

四条实践原则：

1. **单一事实源**：共享类型只定义一次，各端重新导出。避免双份定义各自漂移——这类 bug 编译期无法发现。

2. **兼容缺省值**：新增可选参数要有缺省行为，保证旧调用方不受影响。非法输入回退到安全缺省，而非抛错。

3. **注释写原因**：注释解释「为什么」，不复述「做什么」。尤其记录反直觉的决定和它防的是什么问题。

4. **状态语义要能区分**：不同来源的相似状态必须可区分。「用户主动离开」与「意外中断」若共用一个标记，后续逻辑必然打架。

### 阶段 4：验证（可执行，非人工点验）

**未经执行验证的功能视为未完成。** 声称「应该没问题」不构成交付。

编写脚本化回归，产出机器可判读的结论：

- 逐项输出 `PASS` / `FAIL` 加实际值（不只是布尔，要带上观测到的数据）
- 汇总行输出 `ALL PASS (N checks)` 或 `FAILED n`
- 全通过退出码 0，否则非 0，便于串入流水线

验证要覆盖的四类场景：

| 类别 | 说明 |
|---|---|
| 正向 | 需求描述的主路径 |
| 差异 | 同一操作在不同模式/配置下的表现差异 |
| 边界 | 时限到期、集合为空、目标已销毁 |
| 恶意 | 伪造凭证、越权访问、绕过限制 |

优先选择贴近真实的验证层级。能用真实协议交互就不要 mock；确实需要观察内部状态时，再直接驱动核心对象。

**过时断言必须更新，不能删除。** 断言失败若源于本次刻意的行为变更，应改写为新行为的断言并在提交信息中说明；直接删掉会永久丢失该路径的覆盖。

### 阶段 5：回归与交付

改动完成后跑**全量**既有回归，而非只跑新增的。跨特性破坏往往出现在你认为无关的地方。

同时确认：类型检查、构建、lint 三项通过。

## 关键判断准则

**发现既有缺陷时先报告再修**。测试常会暴露与当前需求无关的老问题。修掉它，但在提交信息中单列一段说明，让它可被追溯。

**用数据反驳直觉**。怀疑某种情况不会发生时，跑统计验证而非假设。例如怀疑某类资源从未被使用，就采样统计其出现频次。

**诚实报告限制**。存在已知边界（如某种场景无法覆盖）时主动说明，并给出可选的改进方向，而不是掩盖。

## 反模式

以下做法会导致返工，应避免：

1. 需求模糊就开始写代码，边写边猜规则
2. 声称完成但未执行任何验证
3. 只跑新增测试，不跑既有回归
4. 删除失败的断言而非更新它
5. 放宽限制时不评估滥用可能
6. 用户的选择有漏洞时照做而不指出
